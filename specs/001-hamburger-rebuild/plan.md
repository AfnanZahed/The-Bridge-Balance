# Implementation Plan: Hamburger Drawer Rebuild

**Branch**: `001-hamburger-rebuild` | **Date**: 2026-08-19 | **Spec**: [spec.md](./spec.md)
**Input**: Feature specification from `/specs/001-hamburger-rebuild/spec.md`

## Summary

The hamburger in the top-left of the Docusaurus navbar currently relies on Docusaurus's `MobileSidebar` (only mounted below 996px) plus a CSS `:has()` projection that hijacks the docs sidebar as a desktop drawer. That hack works, but the spec calls for a from-scratch rebuild so the button, drawer, backdrop, and toggle/dismiss logic are explicit and predictable across the full viewport range.

The rebuild ships three files under `edu-site/src/components/SiteMenu/` (button, drawer, shared `useDrawer` hook), one small layout swizzle, and a focused set of CSS additions that follow the Apple-Design fallback pattern already established for the navbar and search panel.

## Technical Context

- **Language/Version**: TypeScript 5.x (already in use across `edu-site/`), React 18.x (Docusaurus default).
- **Primary Dependencies**: `@docusaurus/router` (already installed), `@docusaurus/useBaseUrl` (already installed). **No new dependencies.**
- **Storage**: N/A — the feature is purely presentational.
- **Testing**: Manual Playwright MCP matrix (per `quickstart.md`); `npm run typecheck`; `npx docusaurus build`.
- **Target Platform**: Browser (Chrome, Edge, Safari, Firefox — last two versions), mobile + desktop viewports.
- **Project Type**: Web (Docusaurus site), single repo.
- **Performance Goals**: Open/close transition ≤ 250ms; first-paint of the open drawer ≤ one frame after click; no layout shift outside the drawer.
- **Constraints**:
  - WCAG 2.1 AA (per Principle VII + project budget).
  - Apple-Design purity per Principle VII: blur with non-blur fallback, reticent motion, light/dark parity, focus-visible rings.
  - Free-tier stack (no new packages).
  - Three-file JS/TS source budget (SC-005).
- **Scale/Scope**: A single instance per page. List size is the same as the top navbar (~5–8 entries).

**Structure Decision**: Option 2 (Web application). The site is a single Docusaurus app; the new component lives in `edu-site/src/components/SiteMenu/`, alongside `BrandMark/` and the other existing components. We avoid Option 1 (a generic `src/`) because Docusaurus expects components under `src/components/` and `src/theme/` for swizzling.

- **Removed** (in the same change):
  - The desktop-only `body:has(.navbar.navbar-sidebar--show) .theme-doc-sidebar-container` projection in `custom.css` (lines ~1454–1482).
  - The `top:0; bottom:auto; height:100dvh` viewport-anchor override on `.navbar-sidebar` / `.navbar-sidebar__backdrop` in `custom.css` (lines ~1438–1444) — these remain in place only as long as the swizzled Navbar continues to mount the default MobileSidebar at mobile widths. After the rebuild, those rules can be deleted if the swizzle no longer mounts `MobileSidebar` at all.

### Architectural Significance

This rebuild is **not** an architecturally significant change in the ADR sense:
- No new framework, no new language, no new service, no new persistence, no new auth boundary.
- The change is local to one component directory and one swizzle.

However, two decisions **do** deserve a future ADR if they evolve further:
- **D-1**: Swizzling `Navbar/Content` rather than the more invasive `Layout` swizzle. If we ever need a second drawer (e.g., command palette), revisit.
- **D-2**: Replacing the CSS `:has()` projection hack with a real component. If we discover other Docusaurus responsive-mounting bugs, the same pattern (swizzle + dedicated component) should be the rule; document this as an ADR after the implementation ships.

These are flagged as **Optional follow-ups**, not blockers.
