## Prompt

"the right and left bars are beautiful, but the middle chapter text is not beautiful, the fonts, the headings, the Sub headings, the organization, the formation, the beauty is not as good and the left and side bars."

Scoped to the chapter reading column, with the bars explicitly named as the quality bar to reach. Routed as `/design typeset`.

## Response snapshot

**Diagnosed before decorating.** Two mechanics turned out to govern the whole block, and both were wrong:

1. **The container hook.** The prose rules were scoped to `article`, which does wrap the content — but every *shape* rule inside assumed sibling relationships that do not exist. Docusaurus renders `<article><nav breadcrumbs/><div class="theme-doc-markdown markdown"><header><h1>…`. So `article h1 + p` — the dek rule meant to set the paragraph under the title larger and muted — **never matched a single chapter**, because a paragraph after `</header>` is not a sibling of the h1. The rule had been dead since it was written. The shape that exists is `header + p`. That also covers intro-2, which opens with a pull-quote, and the Stage 1–4 chapters, which open with `> **Core idea:**`.

2. **Specificity.** Infima ships `.markdown>h2`, `.markdown>h3`, `.markdown>p` and `.markdown li+li` at (0,1,1). A plainer `article h2` is (0,0,2) and loses, so its margins silently reverted to Infima's regardless of source order. Fixed by matching Infima's selector shape on `.theme-doc-markdown > h2` etc. — the same lesson the sidebar block already records for `.menu__link--active`.

**What was actually designed:**

- **Body** 1rem → 1.0625rem (17px) at 1.8 line-height, with 1.85 and slightly looser tracking in dark mode (light-on-dark reads optically thinner). Across 2,400–4,500 word chapters this is the single biggest readability change.
- **Measure** capped at 38rem (~68 characters, inside the 60–75ch band) on `article`, so breadcrumbs, prose and pagination share one column instead of drifting.
- **Section numbering.** Each h2 carries a mono ordinal (01, 02, …) from a CSS counter, in the same voice as the sidebar's chapter ordinals — so the chrome and the prose count position in one system. Verified: 8–13 h2s per chapter, all counted.
- **Rule moved above the heading** instead of underlining it. A chapter has 12–14 h2s; underlining every one gives the reader 12–14 competing horizontal lines.
- **h4 stepped out of the size scale.** At 1.0625rem it was within a pixel of body text — invisible as a heading. It now takes the uppercase tracked eyebrow treatment the chrome already uses for labels.
- **Tables** got tabular figures and real cell padding; **dek** and **lists** got `text-wrap: pretty`.

**Two defects found while verifying, one serious:**

- **A regression I introduced:** rewriting `article pre` to `> pre` broke the code-block frame, because Docusaurus nests it as `div.theme-code-block > div.codeBlockContent > pre`. Caught by a `pre: null` in a computed-style probe, not by eye. Fixed by targeting the container.
- **The light Prism theme was off-system and failing AA.** Stock `github` paints code on #f6f8fa — a blue-tinted gray in a design system built on a neutral silver ramp, and the most-seen colour in the reading column (38 fences). Worse: **23 of its 29 tokens fail WCAG AA 4.5:1 on its own background** — teal at 2.58, blue at 2.69, comments at 2.71. The dark theme had been migrated to a muted palette; light never was. Replaced with a palette measured against silver-2, every token passing (tightest: the italic comment at 4.64), mirroring the dark theme's intent rather than inventing a second scheme.

**The find that mattered most, and it was not a design bug.** While probing why the code block would not go dark, the page threw `TypeError: Cannot read properties of undefined (reading 'data')` and React never hydrated — on **every page, in the production build**. The bundle contained React Fast Refresh HMR code (`e.hot.data && …`), and `module.hot` is undefined in production, so the whole bundle died before hydration. Cause: the persistent webpack cache (`node_modules/.cache`) had been populated by a dev server and reused by the production build. Fixed with `docusaurus clear` plus a clean rebuild, with the dev server stopped first. Re-verified by the theme toggle going from `disabled` to enabled and actually flipping the theme, with zero console errors. **This was pre-existing and unrelated to the typography work** — it would have broken theming, search and the drawer for every real visitor.

**Discipline note.** Twice I read a downscaled screenshot as showing light code blocks on a dark page and nearly "fixed" a bug that did not exist. Both times, sampling the actual pixels (rgb 22,22,24 on a 0,0,0 page) proved dark mode correct. The wrong instinct was to trust my eye over the measurement; the fix was to measure with the element's own bounds rather than guessed coordinates.

## Outcome

- ✅ Impact: the reading column now matches the quality of the bars. Body 17px/1.8 at a 68-character measure, a section-numbered heading system that ties the prose to the chrome's own ordinal language, one neutral code surface shared by inline and block code, and light-mode syntax colours that clear AA instead of failing 23 of 29 tokens.
- 🧪 Tests: chapter gate 5/5 clean; full build green; typecheck clean; axe 0 violations at every impact level on all five chapters; hydration confirmed by toggle; computed styles and pixels both measured.
- 📁 Files: `custom.css` (prose block) and `docusaurus.config.ts` (light Prism palette). No content files touched — this was presentation only.
- 🔁 Next prompts: run `npm run test:a11y` and `npm run test:perf` against the served build for the full audit; consider whether the new section ordinals should also appear in the right-rail TOC; and decide whether the intro chapters should become a sidebar sub-category for consistency with Stage 1–4 (still an open question from the previous turn).
- 🧠 Reflection: the chapter body looked unfinished because two rules were never running — a selector that matched nothing, and a host rule that silently outranked it. Neither is visible by reading the CSS, and a greyscale screenshot would not have distinguished them. The lesson worth keeping: when a surface "has no design", check whether the design is simply not applying before writing a new one.

## Evaluation notes (flywheel)
