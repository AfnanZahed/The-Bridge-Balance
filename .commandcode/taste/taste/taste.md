# Taste
- Wants every referenced file read **in full** before any action is taken; work must come from the actual source files, never from a summary or from memory of "how this kind of thing is usually done." Confidence: 0.9
- Splits large tasks into explicit phases — finish and verify the mechanical/scaffolding work (wiring, references, build green) before starting any creative or authoring work. Confidence: 0.8
- Prefers content authored one unit at a time, in order, pausing for the owner to review each on localhost before the next one begins (later units are assumed to depend on earlier ones being settled). Confidence: 0.85
- When a project ships its own process or authoring skill, expects it to be mastered from its real files and followed exactly, not paraphrased. Confidence: 0.8
- Expects a dated record filed for every prompt and after each major milestone, following the project's existing convention (ID numbering, template shape). Confidence: 0.8
- Respects "no version control" repos: never runs git or other VCS commands in a project that has none by design. Confidence: 0.8
- Never states or implies a fixed chapter count or a finalized table of contents, even implicitly. Confidence: 0.8
- Generates no images, diagrams, SVG, or Mermaid — all visuals are the owner's; a section that would benefit from a diagram ships text-only and names the gap. Confidence: 0.9
- Generated artifacts (manifests, indexes) are regenerated via their script and never hand-edited. Confidence: 0.8
- When files are renamed or retired, expects every reference to them updated — ledgers, contracts, sidebars, docs, glossaries — so nothing live points at a dead path, and expects latent defects surfaced by the change to be fixed and documented. Confidence: 0.85
- Prefers new dated notes **appended** to files that already carry a history of prior notes; prior history must never be silently overwritten. Confidence: 0.85
- Prefers truthful documentation over silently mismatched docs: state what is actually true now (e.g. mark an anchor unset) rather than preserve a stale claim. Confidence: 0.8
- Examples must be real and named — no `foo`, no Acme Corp, no to-do-app stand-ins. Confidence: 0.85
- Every technical term is glossed inline at first use, in every chapter, because readers may arrive from a search result with no earlier context. Confidence: 0.8
- Bans audience-labeling phrases ("if you're new to this," "experienced readers will know"); one document must serve both a senior engineer and a complete beginner. Confidence: 0.8
- Factual claims — etymology, historical lineage, statistics — are verified against real sources before being asserted in prose. Confidence: 0.75
- When previewing a local dev server, wants it opened explicitly in **Microsoft Edge**, not the OS default browser (and the server started without auto-opening one). Confidence: 0.7
- Previews the docs site through its local dev server and expects it reachable at **`localhost:3000`** (Docusaurus `npm start`); keeping a stable, memorable preview URL matters to him — he asks for it by port ("run the localhost 3000") and expects the server started for him. Confidence: 0.7
- Wants significant decisions surfaced for the owner to approve rather than acted on unilaterally — propose the ADR/decision text, never auto-create it; likewise he approves a written plan before implementation (both requests in this session were planned and approved first). Confidence: 0.75
- Plans are expected to be concrete and implementation-ready: exact file paths, code snippets, the reasoning behind each value, and an explicit verification section — not a prose description of intent. Confidence: 0.55
- Comfortable parallelizing work across background subagents to go faster, but expects their status and output verified against real artifacts on disk — never trusted from a handback or from the agent's own claim that it ran. Confidence: 0.75
- Delegation is a speed lever, not a requirement: content to abandon subagents and have the primary agent do the work directly when they are unreliable or unverifiable ("forget the subagents, do yourself"). Confidence: 0.7
- Prefers steady progress to completion — short "continue" / "complete the tasks" nudges, and an expectation that the agent drive its todo list to done and "finish the task carefully and responsibly" rather than stall on process or over-engineer orchestration. Confidence: 0.65
- Expects visual quality to be uniform across a whole site: if the surrounding chrome (navbar, sidebars) is polished, the main reading column must reach the same standard — a mismatch between surfaces reads as unfinished and is worth fixing (he calls out that the "beautiful" sidebar sits next to plain content headings). Confidence: 0.7
- Treats long-form typography and content organization (fonts, heading and subheading hierarchy, rhythm, layout, emphasis, ink) as first-class deliverables rather than cosmetic polish; a plain "this text is not beautiful" report is a legitimate work item, not decoration. Confidence: 0.7
- Treats the project's own design constitution / design law as binding for any styling change: restraint and a monochrome palette with one focused accent per surface, light/dark parity, no gratuitous motion, blur fallbacks wherever blur is used, and no dead utility classes added "just in case." Confidence: 0.7
- Expects UI changes validated against the rendered result in **both light and dark mode** (screenshots of the built site, built HTML inspected), not just a green build or passing tests. Confidence: 0.65
- Expects the project's full gate suite run before work is called done — typecheck, lint, production build including its content gates, and the a11y (axe) check — with pre-existing repo-wide failures explicitly separated from regressions this change introduced. Confidence: 0.7
- Expects design values (type sizes, size caps, spacing) to be justified by measurement rather than guessed — e.g. a heading cap chosen by counting how many lines the longest title wraps to — and recorded in the source comments / type-scale table. Confidence: 0.55
- Expects scratch artifacts from a task (temp scripts, probe/screenshot files) cleaned up and the working tree confirmed to hold only the intended changes. Confidence: 0.5
- Hands over UI work as complete, ready-to-paste code (e.g. a whole Aceternity component, or a literal font/utility-class rule like `.archivo-black-regular`) rather than a description of the desired effect, and expects it wired in as given. The same goes for raw design assets: he drops a file path (e.g. a font ZIP in `Downloads`) and expects it inspected, license-checked, vendored into the repo, and wired to the exact elements he named. Confidence: 0.6
- When he supplies a reference component (e.g. a paste from 21st.dev), wants its visual look kept as given — chose the paste's literal multi-hue palette over the site's token/single-accent system when the two conflicted, and rejected a ported version outright because the original "is more beautiful than the one you have built in my web." So fidelity to the reference outranks internal design-system consistency and any "improvement" made in the name of correctness (though structural/technical fixes needed to make it work are acceptable). Confidence: 0.6
- Judges visual work by comparing the rendered result side by side against his reference, not against the spec or a green test suite: a port that passes every check but reads smaller/fatter/different from the original is wrong to him. A fidelity fix must not be allowed to change *why* the original looked good. Confidence: 0.6
- Expects the content organization to be settled **before** any writing starts: the lesson taxonomy/types (theory, workshop/practice, etc.), their mix, the formatting, and the method must all be decided up front. Unresolved questions here read to him as "confusion, randomness, assumptions and mismanagement at every stage," and he holds the work to an "ultra ordinary" standard of organization, not merely a good one. Confidence: 0.6
- Judges a curriculum/lesson sequence by the real timeline of events, inventions and innovations: material must be taught in the actual order things happened, and coverage checked against the stated purpose/curriculum. Wrong ordering, a bad starting point, or missing pieces are defects to be surfaced, not glossed over. Confidence: 0.6
- Gives visual adjustments as relative, qualitative deltas ("make the headings' text color 30% more blacker") and expects them translated faithfully into the design tokens for **both** light and dark mode — not eyeballed, and not applied literally where a literal reading would be wrong. When he is not fully satisfied with the first pass he iterates on the same dial rather than re-deciding the design. Confidence: 0.6
- edu-site typography is a standing design decision, not a one-off: main chapter titles render in his chosen self-hosted display face (Black Ops One, vendored with its OFL license), subchapter/subtopic headings in the condensed face (Oswald), and every heading level sits at weight 400 with a tinted heading-ink token — he asked for the heading ink to be deepened, so pure-black headings read as too washed out; rank should come from size and colour, not stroke weight. Confidence: 0.6
