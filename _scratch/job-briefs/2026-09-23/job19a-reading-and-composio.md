# Job 19a — what "Reading" can mean, and Composio's free plan (research, 23 September 2026)

## Part 1 — can the book call its core skill "Reading"?

**1. The dictionary senses.** "Read" is "to receive or take in the sense of (letters, symbols, etc.)", and it has well-established figurative senses: "to interpret the meaning or significance of" (read palms), and "to learn the nature of by observing outward expression or signs" — "reads him like a book", "a good canoeist reads the rapids", "a golfer reading a green" — https://www.merriam-webster.com/dictionary/read (senses 1a, 2a, 3). The noun "reading" carries the activity *and* the interpretation: "the way in which you understand a book, situation, etc. (synonym: interpretation) — 'My own reading of events is less optimistic'", and "a closer (= more detailed) reading of the text" — https://www.oxfordlearnersdictionaries.com/definition/english/reading_1. Cambridge separates the same two senses: WRITTEN TEXT, "the skill or activity of getting information from books", and UNDERSTANDING, "the way in which you understand something" — https://dictionary.cambridge.org/dictionary/english/reading. So "read a situation", "read a map" (Oxford's own example is "map reading") and "a close reading" are ordinary English senses, not a stretch.

**2. "Reading literacy" in international education standards — the OECD PISA definition, exactly.** "Reading literacy is understanding, using, evaluating, reflecting on and engaging with texts in order to achieve personal objectives, enhance knowledge and capabilities, and contribute to society" — https://www.oecd.org/en/topics/reading-literacy.html. The 2018 wording, which the OECD says "has remained much the same", reads "…in order to achieve one's goals, to develop one's knowledge and potential, and to participate in society" — https://www.oecd.org/en/publications/how-does-pisa-define-and-measure-reading-literacy_efc4d0fe-en.html. **Understanding, evaluating and reflecting are inside the official definition, by name.**

**3. "Code reading" and "program comprehension".** Reading code is most of the work: 58–70% of a developer's time (Xia 2018; Wyrich 2023) — https://tobiasduerschmid.github.io/SEBook/development_practices/code_comprehension.html — and "most of a software engineer's time is spent reading code"; you must "read a function and know what it will do with its inputs… read a class and understand its state and functionality… comprehend a whole implementation, understanding its architecture"; experts "use prior knowledge… about architecture, design patterns, and the problem domain" — https://andrewbegel.com/info461/readings/comprehension.html. Spinellis's *Code Reading* (Addison-Wesley, 2003) devotes whole chapters to **Tackling Large Projects** (design and implementation techniques, build process, revision control, testing) and **Architecture** (system structures, control models, packaging, design patterns, architecture reuse) — https://www.spinellis.gr/codereading/toc.html. Google's code-review guidance judges by reading alone: "the most important thing to cover in a review is the overall design", "making sure that there are no bugs that you see just by reading the code", "don't accept CLs that degrade the code health of the system" — https://google.github.io/eng-practices/review/reviewer/looking-for.html. **So yes: understanding the logic, the intent, the architecture and the design decisions — and judging correctness and quality — are all inside "reading".**

**4. The limits.** **Hard limits:** reading always *takes something in*; it never writes, runs, ships or owns. Merriam-Webster's computing sense is exact — "read-only: capable of being viewed but not of being changed or deleted" — https://www.merriam-webster.com/dictionary/read-only — and reading produces no artefact that anyone can be held to. **Soft limits:** with context (the domain, the patterns, the intent) reading reaches judgement, because PISA's "evaluating" and Google's review list both judge design and quality. **Directly, does "reading" cover making great architectural and engineering decisions? No.** Judging a decision that already exists is inside reading; choosing what should exist, and carrying the consequences, is a level above it — the revised Bloom's taxonomy puts "Evaluating: making judgments based on criteria and standards" *below* "Creating: putting elements together to form a coherent or functional whole… generating, planning, producing" — https://tips.uark.edu/using-blooms-taxonomy/. **The honest word for that upper half is "judgment"**: "the act or process of forming an opinion or evaluation by discerning and comparing… an opinion or decision that is based on careful thought" — https://www.merriam-webster.com/dictionary/judgment. The book already uses that word with readers: the homepage hero reads "Lead AI agents with **engineering judgment**" — `edu-site/src/components/HomepageHero/index.tsx`.

**5. How a Pakistani student hears it.** Urdu **پڑھنا** (parhna) means to read *and* to study: "to read (a book etc.); to read out aloud; (by extension) to decipher, understand; to study, learn; to recite (a religious or sacred poem or verses of the Quran); to pray" — https://en.wiktionary.org/wiki/پڑھنا. **سمجھنا** (samajhna) is the separate word for understanding itself: "to understand, to comprehend, to perceive, to think" — https://en.wiktionary.org/wiki/سمجھنا. Cambridge's Urdu translation of "reading" is مطالعہ (کتابیں پڑھنا) — https://dictionary.cambridge.org/dictionary/english/reading. So "Reading" lands as a study word, not a strange one — and "reading *and* understanding" is not a redundancy to Urdu ears, because parhna and samajhna are different words. The one real risk: parhna also means reciting by heart, so "Reading" alone can sound like "learning by reading rather than judging".

**6. The book's own definition and rules.** `curriculum-state/canon/thesis.md` line 63 defines the skill: "the ability to read code — whoever or whatever wrote it — and judge it well enough to verify it and take ownership"; line 69 rules its name in: "these are **internal names, not reader-facing ones**… Never put one in front of a reader without deciding deliberately what to call it for them, and asking the owner first." `curriculum-state/canon/naming.md` Rule 1: a reader who has not read the content must understand the name alone, in plain words a beginner already owns; and its "Never put an internal label in a name" list bans "Reading and Understanding Literacy" verbatim. `curriculum-state/canon/course-structure.md` CS-20 (line 138): "the student writes it by hand first, then builds it with a coding agent". `edu-site/src/components/HomepageHero/index.tsx`: heading "Lead AI agents with engineering judgment."

**7. Three candidate reader-facing names**

| Candidate | The one line a student sees | Pros | Cons | Passes naming.md Rule 1? | Is "Reading versus Writing" honest? |
|---|---|---|---|---|---|
| **A. Reading** | "Reading: understand what code does, and decide whether to trust it." | The owner's word; short; every dictionary sense above supports it; the same word PISA uses. | Thin alone: nothing in the word says *judging*; parhna also means reciting; a student may hear school "reading comprehension", not engineering. | Yes, but only with the one-line definition under it. | Half honest: true against *syntax*, false against this book's own students. |
| **B. Reading Literacy** (the owner's) | "Reading Literacy: read code — whoever or whatever wrote it — and judge it." | Plain-looking; matches an international standard's vocabulary; sounds like a course outcome. | "Literacy" points at school reading and writing; it is the internal label thesis.md line 69 forbids, and naming.md bans this exact label; two abstract nouns in a row. | Fails as written — "literacy" is not a beginner's word, and the label is banned. | Silent about producing anything, so it reads as "we do not write code". |
| **C. Reading and Judging Code** (proposed) | "Reading and Judging Code: understand a program, then decide — out loud, with reasons — whether it is good enough to keep." | Names both halves the canon defines, so it promises neither more nor less; "judgment" is already the reader-facing hero word; nothing internal in it. | Longer; "judging" needs the one-line definition so it does not sound harsh. | Yes — reading, judging and code are words a beginner owns. | Honest: the contrast becomes judgment versus syntax, which is the book's real claim. |

**What this means for the name**
1. "Reading" is safe, accurate, ordinary English: dictionaries, PISA (understanding, evaluating, reflecting) and software engineering (program comprehension, Spinellis, Google's review guide) all back it.
2. It honestly covers understanding the logic, the intent, the architecture and the design decisions, and judging correctness and quality.
3. It does **not** cover making architectural and engineering decisions; that half is "judgment" — which is why the hero already says "engineering judgment".
4. "Reading Literacy" is the one form the book's own rules forbid reader-facing (`thesis.md` line 69; `naming.md`'s banned-label list).
5. Recommend **Reading and Judging Code** (or "Reading" plus a judging line); keep "Reading versus Writing" only as judgment-versus-syntax, never as "we do not write code".

## Part 2 — Composio's free plan, and the two setups

**The free plan (composio.dev/pricing).** $0, no credit card, hard-capped: **100,000 tool calls/month**, **50,000 trigger events/month**, **unlimited connected accounts**, 3 team members, 1M sandbox LLM tokens. Included: 1500+ toolkits, OAuth management (consent, token storage, refresh, scopes), triggers, sessions, Composio-managed apps, custom tools and MCP, self-managed credentials, basic white-labeling, 7-day log retention. **Rate limit: 2,000 requests per minute, per organization** — every authenticated endpoint shares it — https://docs.composio.dev/reference/rate-limits. Watch the shared-OAuth allowance: a **Composio-managed app** covers only the first 20K of the 100K tool calls (10K of the 50K triggers, 1K connections); **your own OAuth app gets the full 100K**.

**What it excludes, and what makes you start paying.** Not on Free: 10,000 requests/minute, unlimited team members, read-only dashboard role, IP allowlist, DPA, BAA, zero data retention, SSO/SCIM, customer-managed keys, custom integrations, 30-day log retention. **Premium tools** (Composio-hosted credentials for paid providers — web search, media generation, browser automation, Google Maps) bill at provider cost + 5% even on Free. **At a cap, usage pauses until the next month** — no surprise bill; you pay when you choose Scale ($29/month, $29 monthly credit, then $0.0003/tool call) or when a premium tool runs. X/Twitter additionally needs your own developer app and X's pay-per-use API (job18).

**(a) Composio's MCP connector in the Claude desktop app.** 1. Sign in / create the free account at composio.dev (**dashboard.composio.dev**). 2. In Claude: **Settings → Connectors → Add custom connector**; name **Composio**, URL **https://connect.composio.dev/mcp** (the button on https://composio.dev/claude pre-fills this same dialog). 3. Click **Add** and sign in — no headers, no API key; it is OAuth. 4. You now have Composio's 7 meta-tools (COMPOSIO_SEARCH_TOOLS, COMPOSIO_GET_TOOL_SCHEMAS, COMPOSIO_MULTI_EXECUTE_TOOL, COMPOSIO_MANAGE_CONNECTIONS, COMPOSIO_WAIT_FOR_CONNECTIONS, COMPOSIO_REMOTE_WORKBENCH, COMPOSIO_REMOTE_BASH_TOOL) — https://docs.composio.dev/docs/composio-connect. 5. To post: ask Claude to post; Composio opens an OAuth link for that app (e.g. LinkedIn); approve it once and the connection persists across sessions. 6. If tools do not appear: check that Composio shows a CUSTOM badge in Settings > Connectors, use **⋮ → Clear cache**, or **⋮ → Disconnect → Remove** and re-add.

**(b) DeepSeek in Command Code, through the SDK or the CLI, with an API key.** *Where the key comes from:* dashboard.composio.dev → sign in at composio.dev → **Settings → Project Settings → API Keys** (project key, sent as `x-api-key`); organization tokens sit under **Organization Settings → General Settings → Organization Access Tokens** (`x-org-api-key`); `composio login` stores a user key (`uak_…`) at `~/.composio/user_data.json` — https://docs.composio.dev/reference/authenticating-to-composio.
- **Route 1, the CLI (shortest for an agent):** `curl -fsSL https://composio.dev/install | sh` — Linux/macOS only, so on Windows run it inside **WSL** — then `composio login` (or `composio login --agent` when no human is present), then `composio search "post to linkedin"` → `composio link linkedin` → `composio execute LINKEDIN_CREATE_LINKED_IN_POST -d '{…}'`; login state stays in `~/.composio` — https://docs.composio.dev/docs/cli.
- **Route 2, the SDK:** `uv add composio` (or the npm package), then `Composio(api_key=os.environ["COMPOSIO_API_KEY"])`; omit `api_key` and the SDK reads `COMPOSIO_API_KEY`, then the key stored by `composio login` — https://docs.composio.dev/docs/quickstart.
- **Route 3, inside Command Code itself:** `cmd mcp add --transport http composio https://connect.composio.dev/mcp` (OAuth, no key; the model — DeepSeek or any other — does not matter, because MCP tools are independent of the model). For a key-authenticated endpoint instead: `cmd mcp add --transport http composio <url> --header "x-api-key: ${COMPOSIO_API_KEY}"`; Command Code resolves `${VAR}` in http headers at runtime, and an unset variable stops that one server with an error naming it. Full command set: `reference/mcp.md` in the bundled command-code-knowledge skill.
**Keeping the key out of every repo file.** (1) Prefer the OAuth routes — Composio keeps tokens in `~/.composio`, Command Code in `~/.commandcode/mcp-tokens.json`. (2) For a real API key, keep it in the user environment (`COMPOSIO_API_KEY`) or in Command Code's own store: `/connect` writes keys to `~/.commandcode/auth.json`, mode 0600. (3) Store the MCP server at `--scope user` (`~/.commandcode/mcp.json`) or the default local scope (`~/.commandcode/projects/<slug>/mcp.json`) — **never `--scope project`**, which writes `.mcp.json` into the repo root to be committed. (4) Never paste a raw secret into a config file: Command Code's `providers.json` refuses a pasted key and accepts only references — `"$ENV_VAR"`, `"{env:VAR}"`, or `"!command"`. (5) The DeepSeek API key is a different key, stored the same way through `/connect` (BYOK) — never in the repo.
